1858 POLICY DOMAIN STANDARDIZATION
====================================
Standardize the policy representation from 4288 slots to 1858 slots throughout
the entire stack. 4288 only lives inside model architecture internals where the
bilinear head shape requires it. Everything that crosses a boundary -- raw cache,
priors, training targets, Python/C++ interface -- operates in the 1858 domain.

This document covers both pyfastchess (C++) and chessbot (Python). The change
touches both repos but is documented here because the C++ side is the foundation
and drives the interface contract.


------------------------------------------------------------------------
BACKGROUND: WHY 4288 AND WHAT IS 1858
------------------------------------------------------------------------

The current policy space is 4288 slots:
  4096 = 64 from-squares x 64 to-squares  (includes queen promotions)
   192 = 8 from-files x 8 to-files x 3 underpromo types (N, B, R)
  ----
  4288 total

The board is always normalized to STM-as-white perspective before indexing.
Black moves have their from/to squares XOR'd with 56 (rank flip) before
the index is computed. This makes the policy space color-agnostic.

Most of the 4288 slots are structurally unreachable -- a bishop can never
move like a knight, a rook cannot teleport diagonally, etc. Of the 4288
slots, exactly 1858 are "sometimes-legal": reachable by at least one piece
type from at least one square in at least one legal position. This is the
same count used by Lc0 and AlphaZero.

The 192 underpromo slots are also overdetermined: the encoding uses
8 from-files x 8 to-files but only straight push (df=0) and diagonal
captures (|df|=1) are legal, so only 24 of the 192 are ever reachable.
The sometimes-legal mask already handles this -- they are included in the
1858 count.

Pawn 7th-rank to 8th-rank moves in the 4096 region encode queen promotions
by default. The 192 underpromo region handles the rare knight/bishop/rook
underpromotion cases.

Current waste: 4288 - 1858 = 2430 slots that are allocated, stored,
transmitted, and masked at every boundary but never carry signal. The
sometimes-legal mask exists specifically to zero these out before softmax.


------------------------------------------------------------------------
THE CORE MAPPING: kRemap[4288]
------------------------------------------------------------------------

The bridge between the 4288 computation and the 1858 domain is a static
lookup array:

  static const uint16_t kRemap[4288];  // 8KB, fits in L1 cache

Generation (one-time, at startup or compile time):
  counter = 0
  for i in 0..4287:
    if sometimes_legal[i]:
      kRemap[i] = counter++
    else:
      kRemap[i] = 0xFFFF   // sentinel: never-legal slot

Result: exactly 1858 entries with values 0..1857. All others are 0xFFFF.
The ordering of the 1858 slots follows the natural ordering of the 4288
space -- first sometimes-legal slot gets index 0, second gets 1, etc.
This ordering is stable as long as build_sometimes_legal_mask() does not
change, which it must not.

Usage in C++ hot path (legal_move_mask / moves_to_indices):
  // existing code computes flat_4288 via STM-flip + arithmetic
  uint16_t idx_1858 = kRemap[flat_4288];
  // assert(idx_1858 != 0xFFFF) -- legal moves always map to valid slots

The array lookup is a single L1 read. No string hashing, no arithmetic
beyond what is already done to compute flat_4288. Cost is negligible.

Initialization:
  build_sometimes_legal_mask() is pure deterministic arithmetic with no
  external dependencies, so kRemap can be initialized as a file-scope static
  at program startup (first call to any encoding function, or in a module
  init). A simple pattern:

    static const uint16_t kRemap[4288] = build_kRemap();  // once at startup

  Where build_kRemap() iterates build_sometimes_legal_mask() and assigns
  counters. Since kRemap is read-only after initialization and initialized
  before any MCTS thread starts, no locking is needed. Do not initialize
  lazily inside the hot path -- pay the cost once at startup.

  The table must be identical across C++ and Python. Generate the Python
  dict from the same build_sometimes_legal_mask() source and cross-check
  that kRemap[sl_idx[i]] == i for all i (Test 1) before committing either.

Usage in Python (training, encoding utilities):
  A dict[str, int] mapping STM-perspective UCI string -> 1858 index.
  Generated once from the same kRemap logic applied to a full enumeration
  of sometimes-legal moves. The black-to-move flip is embedded at generation
  time: for each sometimes-legal slot, construct the STM-perspective UCI
  (flipping ranks for black) and store that as the key. Result is one dict
  that accepts raw board UCIs for white and pre-flipped UCIs for black,
  OR two dicts (white_uci->idx, black_uci->idx) taking raw board UCIs
  directly. Either approach is fine since Python encoding is not in the
  200M/min hot path.


------------------------------------------------------------------------
WHAT CHANGES: C++ (pyfastchess)
------------------------------------------------------------------------

backend.hpp / backend.cpp:

  LegalMaskandMap::uci_idx_pairs
    .second currently stores uint16_t in [0, 4287].
    After: stores uint16_t in [0, 1857].
    No struct signature change needed -- same field, smaller domain.

  legal_move_mask() (backend.cpp)
    After computing flat_4288 via STM-flip + arithmetic, apply kRemap:
      uint16_t idx = kRemap[flat_4288];
    Store idx in uci_idx_pairs. No other changes to the function.
    Note: the mask vector (all 4288 bytes) should be dropped per
    EFFICIENCIES.txt item 2. Do both in the same pass.

  moves_to_indices() (backend.cpp)
    Same remap at the end of each move:
      out.push_back(kRemap[flat]);
    Return type stays vector<uint16_t>, values are now [0, 1857].

  build_sometimes_legal_mask() (backend.cpp)
    Keep as-is. Still used by Python model constructors to get sl_idx
    (the 1858 positions within 4288 used for scatter/gather in models
    that have not yet been updated). Mark it as a transitional utility
    to be deprecated once all model variants are converted.

  TOTAL_MOVE_SPACE constant (backend.hpp)
    Keep for now -- still describes the internal model width. Consider
    renaming to MODEL_POLICY_DIM or similar to clarify it is a model
    internal, not the interface width.

cache.hpp / cache.cpp / singleton_registry:

  RawEntry::p_policy
    Currently vector<float> of size 4288.
    After: size 1858.
    raw_cache_bulk_insert_np() shape check: != 4288 -> != 1858.
    raw_cache_lookup() returns 1858-length array.
    Memory per raw cache entry: 17.2KB -> 7.4KB (~57% reduction).
    At 1M entry capacity: ~10MB saved, substantially better hit rate.

  CacheEntry (priors cache)
    Unaffected. Priors are stored as vector<PriorEntry> keyed by UCI
    string. The 1858 index is an encoding detail, not stored in priors.

mcts.cpp:

  build_priors()
    No logic change needed. It iterates pairs and indexes policy_vec[p.second].
    With p.second now in [0, 1857] and policy_vec now size 1858, it just works.
    This is the cleanest part of the migration.

binding.cpp:

  raw_cache_bulk_insert_np()
    Shape check line: p.shape(1) != 4288 -> p.shape(1) != 1858

  raw_cache_bulk_insert() (the Python-iterable version)
    policy.size() != 4288 -> policy.size() != 1858

  raw_cache_lookup()
    Returns 1858-length numpy array instead of 4288.

  emulate_nn_result() (mcts.cpp / binding.cpp)
    Called from Python per move for logging: data["nn_raw_priors"] = nn["raw_priors"].
    Reads directly from the raw cache and reconstructs raw priors by indexing
    policy_vec[p.second] for each legal move pair. After migration, policy_vec
    is 1858-length and p.second is in [0, 1857] -- no logic change needed, but
    this function must be explicitly tested. If missed, it silently returns
    correct-looking but wrong-length data in game logs with no runtime error.

  legal_move_mask_py() / build_sometimes_legal_mask()
    Keep both. They are debug/inspection utilities and model construction
    helpers. Document that legal_move_mask returns uci_idx_pairs with
    1858 indices but no longer returns a 4288 mask vector (per EFFICIENCIES
    item 2).


------------------------------------------------------------------------
WHAT CHANGES: PYTHON (chessbot)
------------------------------------------------------------------------

model.py -- all variants:

  Every current model variant ends with scatter back to 4288:
    pol = torch.full((B, 4288), -3e4, ...)
    pol.scatter_(1, self.sl_idx.unsqueeze(0).expand(B, -1), legal_logits)
    return pol, val

  After: return legal_logits (1858) directly. No scatter. No 4288 buffer.
  The sl_idx buffer registered on each model can be removed.

  16m-precond-smartgate (prod model) specifically:
    Currently: build 4288 bilinear head -> gather 1858 via sl_idx
               -> smartgate on 1858 -> scatter back to 4288
    After: build 4288 bilinear head -> gather 1858 via sl_idx
           -> smartgate on 1858 -> return 1858 directly
    The gather stays (bilinear head requires 4288 width internally).
    Only the final scatter is removed.

  build_sometimes_legal_mask() calls in model constructors:
    Keep for models still using the gather pattern (bilinear heads).
    Remove for models that already produce 1858 natively (conv-gemm,
    conv-gemm-smartgate, conv-mha-gemm-smartgate, hybrid-conv-attn).
    Those can drop sl_idx entirely.

looper.py:

  format_and_predict():
    raw_cache_bulk_insert_np(keys_np, vals_np, probs_np)
    probs_np is now shape (B, 1858) instead of (B, 4288).
    No other change needed here -- the shape flows through naturally
    once the model returns 1858.

infer_ort_trt.py:
  The ORT/TRT inference backend may validate or reshape model output tensors.
  Check for any hardcoded 4288 output shape expectation. A mismatch here
  produces a runtime shape error that may not clearly identify the source.
  Update any output shape checks or reshapes to 1858.

legacy_models.py:
  Contains older architecture definitions. Audit each for 4288 policy output.
  Either update them to return 1858 (matching the migration) or explicitly
  mark them as excluded from the migration scope and document that they are
  incompatible with the post-migration inference stack. Do not leave them
  silently broken -- a legacy model loaded by mistake will produce 4288
  output that passes into a 1858-expecting raw cache and fails on the
  shape check, which is detectable but confusing.

train_pytorch.py / rescore.py / any file building policy targets:

  Policy targets are currently 4288-dimensional one-hot or softmax vectors.
  After: 1858-dimensional. The target index for a move is kRemap[old_idx]
  or equivalently the 1858 dict lookup on the UCI.

  Existing TFRecord or pkl training data that stores 4288 policy targets
  will need either re-generation or an on-load remap. On-load remap is
  simpler: load the 4288 target, apply kRemap to all nonzero indices,
  reconstruct as 1858. A one-time migration script is preferable to
  permanent on-load overhead.

lc0_to_xc0_tfrecords.py and similar bootstrap scripts:
  Any place that builds a 4288-dimensional target vector must be updated
  to build 1858. These are offline scripts so correctness matters more
  than speed -- use the Python UCI dict for clarity.

scripts/build_never_legal_mask.py:
  Review whether this script is still needed post-migration. The never-legal
  mask was a model-internal artifact. Once 4288 is fully internal to model
  architecture only, the standalone mask script may be obsolete.


------------------------------------------------------------------------
PROD MODEL: WEIGHT SURGERY
------------------------------------------------------------------------

The 16m-precond-smartgate weights do not need retraining from scratch.
The only architectural change is removing the final scatter operation,
which has no weights. The bilinear head, gate, and all trunk weights
are unchanged. Load existing checkpoint, remove scatter from forward(),
verify outputs match on a test position (1858 values == old_pol[sl_idx]).

Start from existing checkpoint for fine-tuning:
  - Policy loss target changes to 1858-dimensional
  - Value loss unchanged
  - A few hundred selfplay games should be sufficient to re-calibrate
    the distribution over the compressed domain. The model already
    implicitly operates in 1858 space -- it just used to scatter back.


------------------------------------------------------------------------
TESTING FRAMEWORK
------------------------------------------------------------------------

These tests should be written and passing before any production change.
Run them as a suite that can be re-executed after each migration step.

Test 1: kRemap table integrity
  - Generate kRemap from build_sometimes_legal_mask()
  - Assert exactly 1858 non-sentinel entries (count of values != 0xFFFF)
  - Assert no duplicate values among the 1858 valid entries
  - Assert values span exactly [0, 1857] with no gaps
  - Assert kRemap[sl_idx[i]] == i for all i in 0..1857
    (sl_idx is the nonzero positions from sometimes_legal_mask)

Test 2: legal_move_mask round-trip
  For startpos and N tactical positions:
  - Generate uci_idx_pairs with new code (1858 indices)
  - Assert all .second values are in [0, 1857] (no sentinel)
  - Assert set of .first values matches board.legal_moves() exactly
  - Assert kRemap[old_idx] == new_idx for every move
    (run old code in parallel during transition to cross-check)

Test 3: moves_to_indices consistency
  For a suite of positions:
  - new_indices = board.moves_to_indices(ucis)    # 1858 domain
  - old_indices = board.moves_to_indices_4288(ucis)  # keep old version temporarily
  - Assert new_indices[i] == kRemap[old_indices[i]] for all i

Test 4: build_priors policy equivalence
  With a frozen model checkpoint:
  - Run old path: model -> 4288 policy -> raw_cache_insert(4288) -> build_priors
  - Run new path: model -> 1858 policy -> raw_cache_insert(1858) -> build_priors
  - For a suite of positions, assert resulting PriorEntry vectors are
    identical (same UCI, same prior float within 1e-5 tolerance)
  - This is the most important test: it confirms end-to-end equivalence

Test 5: perft legal move coverage
  For startpos + at least 10 positions (mix of opening, middlegame, endgame,
  promotion-adjacent, underpromo-possible):
  - Generate all legal moves
  - Assert every move maps to a valid 1858 index (no sentinel hits)
  - Assert no two legal moves in the same position map to the same index
  - Repeat for both white-to-move and black-to-move positions

Test 6: underpromo coverage
  Construct positions where underpromotions (N, B, R) are legal.
  Assert all three underpromo types map to distinct valid 1858 indices.
  Assert the corresponding queen promotion in the same file also maps
  correctly (via the 4096 region, not the 192 region).

Test 7: training target equivalence
  For a sample of saved game logs with 4288 policy targets:
  - Apply on-load remap to get 1858 targets
  - Verify sum of remapped target == sum of original (mass is preserved)
  - Verify argmax of remapped target corresponds to same UCI as argmax
    of original (best move is unchanged)


------------------------------------------------------------------------
IMPLEMENTATION ORDER
------------------------------------------------------------------------

The steps have dependencies. Follow this order to keep the system in a
working state at each step.

Step 1: Generate and validate kRemap (offline)
  Write the kRemap generation in Python first. Run Test 1 and Test 5.
  Validate the table independently before touching any C++ code.
  Lock in the table -- it must not change after this point.

Step 2: Drop LegalMaskandMap::mask, move generation into expand (C++)
  Per EFFICIENCIES.txt items 1 and 2. This is a prerequisite because
  after this step, legal_move_mask() is called once in expand and the
  kRemap application naturally goes there. Do not apply kRemap yet --
  just restructure so there is one movegen pass.

Step 3: Apply kRemap in C++, switch uci_idx_pairs to 1858 (C++)
  Add kRemap as a static array (or generated at startup from
  build_sometimes_legal_mask()). Apply it in legal_move_mask() and
  moves_to_indices(). Run Tests 2 and 3. C++ now speaks 1858.
  Temporarily keep old 4288 path behind a flag for cross-checking.

Step 4: Shrink raw cache to 1858 (C++)
  Update RawEntry, bulk_insert shape checks, raw_cache_lookup.
  Run Test 4 using the Python model still outputting 4288 but sliced
  to 1858 before insert (temporary shim). Confirm build_priors still
  produces correct priors. Remove temporary shim.

Step 5: Update model outputs to return 1858 (Python/chessbot)
  Remove scatter from all model variants. Update looper to pass 1858
  policy to raw_cache_bulk_insert_np. Run Test 4 end-to-end with
  no shim. Confirm selfplay produces sensible games.

Step 6: Update training pipeline (Python/chessbot)
  Update policy target construction in train_pytorch.py and rescore.py.
  Write migration script for existing training data if needed.
  Run Test 7.

Step 7: Fine-tune prod model from existing checkpoint
  Load 16m-precond-smartgate weights. Verify output equivalence (Test 4).
  Run short selfplay session to confirm search behavior is unchanged.


------------------------------------------------------------------------
CALLOUTS AND GOTCHAS
------------------------------------------------------------------------

sometimes-legal != always-legal:
  The 1858 indices cover sometimes-legal slots, not guaranteed-legal moves
  in any given position. At runtime, uci_idx_pairs only contains the subset
  that are legal in the current position. kRemap[sentinel] (0xFFFF) should
  never be hit for a legal move -- if it is, something is wrong with the
  flip or arithmetic. Add an assertion in debug builds.

Castling remapping:
  legal_move_mask() already handles castling: the engine stores the rook
  destination internally but the code remaps to the king's destination
  (e1g1, e1c1, e8g8, e8c8) for the policy index. This remapping happens
  before the kRemap application, so castling is handled correctly.

Underpromo encoding:
  The 192 underpromo region uses file-based indexing (not square-based),
  so the STM flip operates on files (from_file, to_file) not squares.
  kRemap handles this uniformly since the 192 slots are part of the 4288
  space and their sometimes-legal entries are included in the 1858.
  No special handling needed.

Black-to-move STM flip:
  The XOR-56 rank flip on from/to squares (or from/to files for underpromos)
  is applied BEFORE kRemap. kRemap operates on STM-perspective indices.
  Do not apply kRemap to raw board indices -- always flip first.

Model variants not yet converted:
  build_sometimes_legal_mask() and sl_idx are still used by bilinear-head
  models (16m-precond-smartgate) for the internal gather step. These are
  model-internal and are NOT the same as the policy output domain. The
  model gather (4288->1858 internally) and the output (1858) are separate
  concerns. Do not conflate them.

Training data from before migration:
  Any pkl or TFRecord files containing 4288 policy targets must be remapped
  before use. The remap is lossless (1858 covers all sometimes-legal slots;
  no training signal lives in never-legal slots). However, verify this on
  a sample before bulk migration -- if any target has mass on a never-legal
  slot (which should not happen but could indicate a prior encoding bug),
  that mass would be silently dropped.

Raw cache invalidation:
  Any warm raw cache from before the migration contains 4288-float entries.
  After migration the cache expects 1858-float entries. Clear the raw cache
  on startup after deploying the migration. priors_cache_clear() should also
  be called since priors derived from 4288 policies are no longer valid.
  Both caches are in-memory only so this is just a startup call.
